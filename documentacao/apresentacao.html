Criptografador de Senhas Baseado em Dicionário Dinâmico

Instituição: FAETERJ Petrópolis • Disciplina: Sistemas Operacionais II (Avaliação P1) • Aluno: Wallace Duarte Venâncio

Definição Algorítmica do Problema

  • Sistema de criptografia e descriptografia simétrica baseado na geração em tempo real de um dicionário dinâmico massivo em memória RAM (N = 10.000.000 de entradas).
  • Para cada índice i ∈ [0, N), executam-se 50 iterações de aritmética modular com a semente secreta K = 84729: valor = (valor * 31 + 17) % 1000000007.
  • O resultado é formatado como subst_<valor>, invertido in-place e armazenado em estrutura contígua EntradaDic[32] (320 MB).

Diretrizes de Engenharia de Sistemas Operacionais

  • Proibição de Hardcoding: Todos os binários recebem argumentos dinâmicos via CLI: ./app <workers> [tamanho] [chave] [senha].
  • Equivalência Estrita de Dados: Alocação contígua livre de locks de heap (malloc) e saída bit a bit idêntica entre as 3 versões (diff = 0).
  • Três Paradigmas + Cgroups: Sequencial (Baseline ≥ 2s), Processos (fork + mmap), Threads (std::thread + mutex) e Docker (--cpus).

Tópico 2 • Versão Sequencial (Baseline Monothread)

Slide 02 / 10

Arquitetura do Baseline (/sequencial/main.cpp)

  • Executa em um único fluxo de instruções percorrendo sequencialmente i = 0 até 9.999.999 (500 milhões de operações modulares totais).
  • Alocação contígua de struct EntradaDic { char valor[32]; } na heap sem chamadas a malloc dentro do laço crítico.
  • Calcula o checksum_global = 5000000903112875, cifra a senha e realiza a verificação de descriptografia reversa diretamente na memória.
  • Requisito Atendido: Compilado com g++ -O3, atinge Tseq = 3,8621 s ≥ 2,0 s.
// Laço crítico sequencial (N = 10.000.000)
uint64_t checksum_global = 0;
for (long long i = 0; i < tamanho; ++i) {
    long long valor = i * chave;
    for (int j = 0; j < 50; ++j) {
        valor = (valor * 31 + 17) % 1000000007;
    }
    checksum_global += static_cast<uint64_t>(valor);

    char buffer_tmp[32];
    int len = std::snprintf(buffer_tmp, 32, "subst_%lld", valor);
    for (int k = 0; k < len; ++k) {
        dicionario[i].valor[k] = buffer_tmp[len - 1 - k];
    }
    dicionario[i].valor[len] = '\0';
}

Tópico 3 • Estratégia de Paralelização (Decomposição de Domínio)

Slide 03 / 10

Particionamento Estático por Blocos Contíguos Disjuntos (Chunking)

Como o custo computacional de cada posição i é uniforme (exatamente 50 iterações modulares + inversão de string), o balanceamento de carga ótimo é obtido dividindo o domínio [0, N) em P subintervalos contíguos disjuntos:

long long chunk = tamanho / workers;
for (int p = 0; p < workers; ++p) {
    long long start_idx = p * chunk;
    long long end_idx = (p == workers - 1)
                        ? tamanho
                        : start_idx + chunk;
    // Worker p processa exclusivamente [start_idx, end_idx)
}

Exemplo para N = 10.000.000 e P = 4 Workers:

  • Worker #0: [0 .. 2.500.000) → 80 MB
  • Worker #1: [2.500.000 .. 5.000.000) → 80 MB
  • Worker #2: [5.000.000 .. 7.500.000) → 80 MB
  • Worker #3: [7.500.000 .. 10.000.000) → 80 MB
  • Propriedade Fundamental: Interseção vazia entre fatias ⇒ escrita paralela livre de race conditions no vetor!

Tópico 4 • Implementação Paralela com Processos (POSIX)

Slide 04 / 10

Ciclo de Vida: fork(), _exit(0) e Barreira waitpid()

  • O processo pai instancia P processos filhos via syscall fork().
  • Cada filho calcula sua fatia [start_idx, end_idx), atualiza o checksum compartilhado sob exclusão mútua e encerra imediatamente com _exit(0).
  • O processo pai executa uma barreira de sincronização determinística aguardando todos os PIDs via waitpid(pids[p], &status, 0) antes de cifrar a senha.
for (int p = 0; p < workers; ++p) {
    pid_t pid = fork();
    if (pid == 0) { // PROCESSO FILHO
        uint64_t checksum_local = 0;
        for (long long i = start_idx; i < end_idx; ++i) {
            // 50 iteracoes + gravacao em dicionario[i]
        }
        pthread_mutex_lock(&controle->mutex);
        controle->checksum_global += checksum_local;
        pthread_mutex_unlock(&controle->mutex);
        _exit(0);
    }
    pids[p] = pid;
}
for (int p = 0; p < workers; ++p) waitpid(pids[p], NULL, 0);

Tópico 5 • Memória Compartilhada (mmap vs. Copy-on-Write)

Slide 05 / 10

Por que Variáveis Globais / malloc Falhariam no fork()?

  • No Linux, o fork() clona a tabela de páginas do processo pai marcando as páginas privadas como somente-leitura sob semântica Copy-on-Write (CoW).
  • Quando um processo filho escreve em memória privada (heap/global), o kernel gera um page fault e cria uma cópia física isolada invisível para o processo pai!

Solução POSIX IPC: mmap(MAP_SHARED | MAP_ANONYMOUS)

  • Alocamos os 320 MB do dicionário e a estrutura de controle com PROT_READ | PROT_WRITE e MAP_SHARED | MAP_ANONYMOUS antes do fork().
  • As tabelas de páginas de pai e filhos apontam para os mesmos quadros físicos de RAM, permitindo escrita simultânea visível ao pai e liberação via munmap().
size_t dic_bytes = static_cast<size_t>(tamanho) * sizeof(EntradaDic);
EntradaDic* dicionario = static_cast<EntradaDic*>(
    mmap(NULL, dic_bytes, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0)
);

Tópico 6 • Sincronização e Controle de Região Crítica

Slide 06 / 10

Prevenção de Contenção de Lock (Acumulação Local + Redução)

  • Se os trabalhadores adquirissem o mutex a cada iteração do laço (10.000.000 de vezes), a serialização destruiria completamente o paralelismo.
  • Cada worker acumula checksum_local em registrador/pilha privativa durante o laço e entra na Região Crítica apenas 1 vez ao concluir seu bloco.

Primitivas de Exclusão Mútua Utilizadas

  • Em Processos: pthread_mutex_t alocado via mmap(MAP_SHARED) e inicializado com atributo PTHREAD_PROCESS_SHARED.
  • Em Threads: std::mutex gerenciado com idioma RAII via std::lock_guard<std::mutex>.
  • Validação: Checksum idêntico (5000000903112875) em 100% das baterias!
// Inicialização do Mutex Interprocessos (/processos/main.cpp)           // Região Crítica em Threads (/threads/main.cpp)
pthread_mutexattr_t mattr;                                               {
pthread_mutexattr_init(&mattr);                                              std::lock_guard<std::mutex> lock(mtx_checksum);
pthread_mutexattr_setpshared(&mattr, PTHREAD_PROCESS_SHARED);                checksum_global += checksum_local;
pthread_mutex_init(&controle->mutex, &mattr);                            }

Tópico 7 • Implementação Paralela com Threads (std::thread)

Slide 07 / 10

Vantagens do Espaço de Endereçamento Compartilhado

  • Threads instanciadas via std::thread (syscall clone() com CLONE_VM) compartilham nativamente a mesma tabela de páginas e o mesmo heap (EntradaDic*).
  • Menor Overhead de Criação e Context Switch: Não há clonagem de descritores de memória virtual (VMAs) nem descarga de TLB entre threads do mesmo processo.
  • Memória sem mmap: o heap privado gera ~600 minor page faults contra ~78.000 do mmap(MAP_SHARED) (medido), mas esse custo é pequeno (< 0,2 s de tempo de sistema).
std::vector<std::thread> threads;
threads.reserve(workers);
long long chunk = tamanho / workers;

for (int p = 0; p < workers; ++p) {
    long long start_idx = p * chunk;
    long long end_idx = (p == workers - 1) ? tamanho : start_idx + chunk;
    threads.emplace_back(
        processar_fatia_dicionario, dicionario,
        start_idx, end_idx, chave,
        std::ref(checksum_global), std::ref(mtx_checksum)
    );
}
for (auto& th : threads) th.join();

Tópico 10 • Conclusões & Síntese para Arguição Presencial

Slide 10 / 10

1. Lei de Amdahl & Gargalo Memory-Bound

  • A aceleração máxima atingiu 3,44x (Threads) e 3,32x (Processos) com 8 workers.
  • Além da fração sequencial inevitável, a gravação concorrente de 320 MB satura a largura de banda do controlador de memória RAM e o cache L3 compartilhado.

2. Threads vs. Processos (Custos de Kernel)

  • Threads e Processos ficaram muito próximos (3,44x vs 3,32x com 8 workers): o cálculo é o mesmo código; threads têm leve vantagem por criar fluxos mais baratos e dispensar o mmap.
  • Processos exigem mmap(MAP_SHARED) (~78.000 minor page faults, medidos) e IPC explícito, em troca de isolamento de memória entre processos.

3. Efeito de Cgroups (--cpus) e Escalonador CFS

  • Com --cpus="1" (cota de 100 ms por período de 100 ms), instanciar 8 fluxos força o Completely Fair Scheduler a realizar preempções contínuas e trocas de contexto sem paralelismo físico real.

4. Conformidade Integral com o Edital SO2

  • Equivalência bit a bit comprovada (diff = 0), CLI dinâmica sem hardcoding, 135 execuções documentadas em CSV e interface de telemetria livre de interferência de CPU.
