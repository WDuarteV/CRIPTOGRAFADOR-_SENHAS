1. O projeto em linguagem simples

O programa constrói uma tabela gigante (o "dicionário") com 10 milhões de linhas. Cada linha é um texto calculado por uma conta matemática pesada. Depois, para cifrar uma senha, cada letra é trocada pelo texto da tabela naquela posição. Para decifrar, faz-se o caminho inverso e a senha original volta.

O objetivo da disciplina não é a criptografia, e sim comparar três formas de executar o mesmo trabalho e entender o que o sistema operacional faz em cada uma:

VersãoComo executaAnalogia
Sequencial1 fluxo faz tudo1 pessoa copiando um livro inteiro
Processosfork() cria cópias do programa, que dividem a tabela por memória compartilhada (mmap)4 pessoas em 4 salas separadas, escrevendo num caderno compartilhado por um guichê
Threadsstd::thread cria fluxos dentro do mesmo programa4 pessoas na mesma sala, com o mesmo caderno na mesa

Depois medimos tempo, speedup e eficiência no computador (host) e dentro de um container Docker com limite de CPU (--cpus=1, 2, 4), para ver o efeito de ter mais fluxos do que núcleos disponíveis.

Como o programa é chamado (nada fixo no código)

./threads/app <workers> [tamanho] [chave] [senha]
./threads/app 8 10000000 84729 AvaliacaoSO2

2. Glossário: termos técnicos explicados

TermoExplicação simples
CPU-boundPrograma limitado pela velocidade das contas do processador (o nosso: 500 milhões de contas).
Memory-boundPrograma limitado pela velocidade de ler/escrever na memória RAM. É uma possível explicação para o speedup não chegar a 8; não foi medida diretamente.
DicionárioVetor de 10.000.000 entradas de 32 bytes (struct EntradaDic { char valor[32]; }) = 320 MB.
ChecksumNúmero que resume todo o conteúdo. Se as três versões dão o mesmo (5000000903112875), o resultado é idêntico. Funciona como "dígito verificador".
WorkerCada fluxo que trabalha em paralelo (processo ou thread).
Chunking (blocos contíguos)Dividir o intervalo [0, N) em P pedaços seguidos. Com 4 workers: 0–2,5 mi, 2,5–5 mi etc.
Speedup (S)Quantas vezes ficou mais rápido: T_sequencial / T_paralelo. Ex.: 3,86 / 1,12 = 3,44.
Eficiência (E)Speedup dividido pelo nº de workers. 3,44 / 8 = 43%. Mostra quanto do "ideal" foi aproveitado.
Lei de AmdahlSempre existe uma parte que não paraleliza (alocar memória, criar workers, esperar, cifrar). Ela limita o ganho máximo, mesmo com muitos núcleos.
Condição de corridaDois fluxos mexendo no mesmo dado ao mesmo tempo, com resultado imprevisível.
Região críticaTrecho de código que só um fluxo pode executar por vez. No projeto: somar no checksum_global.
Mutex"Chave do banheiro": quem tem a chave entra; os outros esperam. std::mutex (threads) e pthread_mutex_t com PTHREAD_PROCESS_SHARED (processos).
futexChamada ao kernel que o mutex usa quando há disputa e é preciso dormir/acordar. Custa caro se usada milhões de vezes.
Cache / linha de cacheMemória pequena e rapidíssima dentro da CPU. Trabalha em blocos de 64 bytes (linhas).
False sharingDois núcleos escrevem em dados diferentes que caem na mesma linha de cache; a linha fica sendo invalidada de um núcleo para o outro (ping-pong, protocolo MESI) e o programa fica lento.
fork()Cria um novo processo, cópia do atual.
Copy-on-Write (CoW)Após o fork, pai e filho compartilham as páginas até alguém escrever; aí o kernel faz uma cópia privada para quem escreveu. Por isso uma variável comum não serve para comunicar filho → pai.
mmapPede ao kernel uma região de memória. MAP_SHARED: compartilhada entre pai e filhos. MAP_ANONYMOUS: sem arquivo por trás, só RAM.
waitpid()O pai espera o filho terminar e recolhe o status. Evita processo zumbi (filho terminado que ninguém "enterrou").
_exit(0)Encerra o filho direto no kernel, sem descarregar buffers herdados do pai (exit poderia imprimir texto duplicado).
Thread / clone()Fluxo leve que compartilha a memória do processo. No Linux é criado por clone(CLONE_VM).
TLBCache que guarda traduções de endereço virtual para físico. Trocar de processo costuma invalidá-la; trocar de thread do mesmo processo, não.
Page fault (minor)Primeiro acesso a uma página de memória: o kernel precisa mapeá-la. "Minor" = não precisa ler do disco.
THPTransparent Huge Pages: páginas de 2 MB em vez de 4 KB, reduzem faltas de página.
Cgroups / CFS / --cpusCgroups é o recurso do kernel que limita recursos de um grupo de processos. O CFS é o escalonador do Linux. --cpus=1 dá uma cota de 100 ms de CPU a cada 100 ms para o container inteiro.
Troca de contextoO kernel pausa um fluxo e coloca outro no núcleo. Tem custo.
SobreassinaturaTer mais fluxos do que CPUs disponíveis. Eles se revezam e o desempenho piora.
SMT / Hyper-Threading, P-core e E-coreAlguns núcleos físicos aparecem como 2 lógicos (e dividem recursos). Nosso i5-1235U tem 2 P-cores (rápidos, 4 threads) e 8 E-cores (mais lentos), totalizando 12 threads lógicas e núcleos não idênticos.
-O3 e inlining-O3 é otimização máxima do g++. Inlining é o compilador "colar" uma função dentro de outra; às vezes muda o código gerado para pior ou melhor.
malloc / heapAlocação dinâmica de memória. O alocador usa travas internas; muitas threads alocando ao mesmo tempo disputam essas travas.
std::chronoRelógio de alta precisão do C++ que mede os tempos dentro do próprio programa.
Map-reduce localCada worker soma sozinho (map) e só no final junta o resultado na variável global (reduce), usando o mutex uma única vez.

3. Perguntas e respostas

Bloco 1 — Problema e versão sequencial

1. Explique o seu problema em poucas palavras.
Criptografador baseado em dicionário. Para cada posição i de 0 a N−1, faço 50 contas valor = (valor × 31 + 17) % 1000000007, formato o texto subst_<valor>, inverto e guardo na tabela. Cifrar uma senha é trocar cada letra pela entrada da tabela correspondente; decifrar é o caminho inverso (e o programa confirma que a senha original volta).
Simples: é uma tabela de códigos secreta, gerada por conta pesada, usada para trocar letras por códigos e vice-versa.
2. Por que 10 milhões de posições e 50 iterações?
O edital exige que o sequencial leve pelo menos 2 s com g++ -O3. Se a conta fosse leve, o programa terminaria em milissegundos e o custo de criar processos/threads seria maior que o trabalho, escondendo o speedup. Com 500 milhões de contas, o sequencial leva cerca de 3,86 s.
Simples: é preciso trabalho suficiente para valer a pena dividir.
3. Por que cada iteração depende da anterior?
Cada passo usa o resultado do passo anterior, então o compilador não consegue pular o laço nem calcular tudo de uma vez (vetorizar). Isso garante trabalho real em -O3.
4. Por que não usou std::vector<std::string>?
(1) Cada std::string pode chamar malloc, e várias threads disputariam as travas do alocador, escondendo o paralelismo. (2) A string guarda ponteiros para o heap privado de quem a criou; isso não funciona em memória compartilhada entre processos. Usei struct EntradaDic { char valor[32]; } em um bloco contíguo de 10.000.000 × 32 B = 320 MB, alocado uma vez. Dentro do laço formato num buffer pequeno na pilha e copio, sem nenhum malloc.
5. Os parâmetros estão fixos no código?
Não. Todos usam ./app <workers> [tamanho] [chave] [senha] via argc/argv.
6. Qual a diferença entre "tempo de geração" e "tempo total"?
Geração é só o preenchimento do dicionário (a parte paralela). Total inclui também alocação, cifragem e descriptografia. Na prática são praticamente iguais (diferença de décimos de milésimo a poucos milésimos de segundo, nos CSVs), porque cifrar/decifrar uma senha de 12 letras é desprezível.

Bloco 2 — Estratégia de paralelização

7. Como você dividiu o trabalho?
Dividi [0, N) em P blocos contíguos. O worker p processa de p×chunk até (p+1)×chunk, e o último pega o resto. Com 4 workers: 2,5 milhões de posições (80 MB) cada.
Simples: 4 pessoas copiando um livro, cada uma com um quarto das páginas.
8. Houve condição de corrida na escrita do dicionário?
Não. Os blocos são disjuntos, ninguém escreve na posição do outro. Por isso não precisei de mutex durante o cálculo.
9. Por que blocos contíguos e não intercalados (pares/ímpares)?
Por causa do false sharing. Uma linha de cache tem 64 B e cabem 2 entradas de 32 B. Se dois núcleos escrevessem em posições vizinhas, a linha ficaria sendo invalidada entre eles. Com blocos contíguos, cada núcleo trabalha na sua região; só nas fronteiras entre blocos há vizinhança, o que é irrelevante.

Bloco 3 — Processos e memória compartilhada

10. Descreva o ciclo de vida dos processos.
O pai cria P filhos com fork(). Cada filho calcula seu bloco, soma o resultado no checksum compartilhado (com mutex) e termina com _exit(0). O pai espera todos com waitpid() e só então cifra a senha.
11. Por que mmap(MAP_SHARED | MAP_ANONYMOUS) e não variável global ou new[]?
Por causa do Copy-on-Write: quando o filho escreve numa página privada, o kernel faz uma cópia só para ele e o pai nunca vê. O dicionário do pai ficaria vazio. Com MAP_SHARED, pai e filhos apontam para as mesmas páginas de RAM; MAP_ANONYMOUS faz isso sem arquivo em disco.
12. Por que _exit(0) e não exit(0)?
exit descarrega buffers de E/S herdados do pai e roda destrutores, podendo duplicar saída no terminal. _exit encerra direto.
13. Para que serve o waitpid()?
Duas coisas: serve de barreira (o pai só cifra depois que todos terminaram de escrever) e recolhe o status dos filhos, evitando processos zumbis.

Bloco 4 — Sincronização

14. Onde está a região crítica?
Na soma do checksum_global. Em threads uso std::mutex com std::lock_guard. Em processos uso pthread_mutex_t na memória compartilhada, com o atributo PTHREAD_PROCESS_SHARED; sem ele o mutex só funcionaria dentro de um processo.
15. Por que não trava o mutex a cada iteração?
Seriam 10 milhões de disputas pelo lock, com chamadas futex ao kernel, e o programa viraria quase serial. Cada worker acumula em checksum_local (registrador/pilha) e entra na região crítica uma única vez, ao fim do bloco. Exclusão mútua garantida com custo quase zero.
16. Como prova que as três versões dão o mesmo resultado?
Com diff entre as seções [RESULTADOS] do sequencial, processos e threads: retorno 0 (nenhuma diferença). O checksum 5000000903112875 é idêntico em todas as 135 execuções.

Bloco 5 — Threads

17. Qual a diferença de custo entre criar thread e processo?
O fork() cria uma nova task_struct e duplica estruturas de memória virtual (VMAs, tabelas de páginas). A thread (clone com CLONE_VM) compartilha o espaço de endereçamento: só ganha pilha e TID. Nasce mais barata, e a troca de contexto entre threads do mesmo processo é mais leve (não invalida a TLB).

19. Por que o speedup com 8 workers não foi 8?
(1) Amdahl: há uma parte que não paraleliza (alocação, criação dos workers, barreira, cifragem). Estimativa: com S = 3,44 e P = 8, a fração paralelizável efetiva fica em torno de 81% (f = (1 − 1/S)/(1 − 1/P)). Digo "estimativa", não medição. (2) Os 12 "núcleos" do meu i5-1235U não são iguais: são 2 P-cores com Hyper-Threading e 8 E-cores mais lentos. Medi 1 thread em um P-core = 4,09 s e em um E-core = 5,72 s. (3) 320 MB escritos ao mesmo tempo podem pressionar memória e cache L3 (hipótese coerente, não medida).
20. O que o Gráfico 3 (Docker) mostra?
Com --cpus="1" não há paralelismo físico; só revezamento. Mais workers = pior: 2 / 4 / 8 threads levaram 5,34 / 7,33 / 9,66 s (todos pior que os 3,86 s do sequencial). Com --cpus="2": 2 workers 2,26 s (1,71x), mas 4 e 8 pioram (3,73 e 4,49 s). Com --cpus="4": 4 threads 1,74 s (2,22x) e 8 threads 2,14 s. Moral: mais workers que CPUs disponíveis piora (sobreassinatura, trocas de contexto, cache). O --cpus usa cgroups (cota do CFS).
21. Por que a curva se achata perto de 8 workers?
Pelo conjunto: Amdahl, memória/cache compartilhados e núcleos não idênticos (P-cores e E-cores; SMT divide recursos). Não afirmo um único culpado.
22. Threads ou processos: qual é melhor?
Em desempenho, ficaram praticamente empatados (3,44x × 3,32x). Threads são mais simples e baratas (memória já compartilhada, criação leve). Processos dão isolamento: um erro em um filho não corrompe a memória dos outros (fora da área compartilhada), ao custo de IPC explícito (mmap, mutex compartilhado).

4. Pontos fracos: análise e como responder

Ponto fraco 1 — "Por que 1 processo levou 6,78 s e 1 thread só 3,94 s?" (RESOLVIDO)

O que a análise mostrou: a hipótese THP × 4 KB era frágil, como você suspeitou, e eu a testei:

  • Falhas de página medidas: processos ~78.000 × threads ~600. A diferença existe.
  • Mas o tempo de sistema (kernel) foi só 0,17 s. O tempo extra estava no tempo de usuário (6,7 s × 3,65 s), isto é, no código do programa.
  • Teste decisivo: trocando MAP_SHARED por MAP_PRIVATE, continuou ~6,3 s. Logo, não era a memória compartilhada.
  • Causa real: o laço ficava dentro de main() e o g++ -O3 gerou código mais lento. Movendo o laço para uma função própria noinline (igual à das threads), 1 processo foi para ~3,75 s e 8 processos para ~1,21 s.

Como responder se perguntarem: "Na primeira bateria vi 6,78 s com 1 processo. Medi as falhas de página (78 mil contra 600), mas o tempo de sistema era só 0,17 s, então não explicava. Troquei para MAP_PRIVATE e não mudou. O problema era o código gerado pelo compilador para o laço dentro do main. Isolei o laço em uma função, refiz todas as 135 execuções e agora processos e threads estão praticamente empatados." Isso mostra método científico.

Ponto fraco 2 — "8 threads com --cpus=1 foi mais lento que 1 thread?"

Nos dados novos, sim: 8 threads com --cpus="1" = 9,66 s contra 3,86 s do sequencial (0,40x). Antes (bateria anterior) estava praticamente igual (3,94 s). Não corrija o professor: concorde e explique: com 1 CPU de cota, 8 threads se revezam; há trocas de contexto, perda de cache e a cota do CFS é consumida em fatias de 100 ms. Pense em 8 pessoas dividindo 1 caneta.

Cuidado: 2 threads com 1 CPU também ficou em 5,34 s, bem acima de 3,86 s. Tenho duas hipóteses, não medidas: a sobrecarga de limitar CPU dentro da VM do Docker Desktop e o fato de os núcleos virtuais caírem em E-cores (que medi serem ~40% mais lentos). Diga isso como hipótese.

Ponto fraco 3 — "Memory-bound" e "saturação do barramento"

Não foram medidos diretamente. Resposta: "É a explicação mais coerente com os dados, junto com Amdahl e com os núcleos heterogêneos. Eu poderia confirmar com perf stat (contadores de cache/memória), mas não medi." Nunca afirme como fato.

Ponto fraco 4 — Tabela do Docker mistura P = 2, 4 e 8

Saiba dizer: o Gráfico 3 tem 2, 4 e 8 workers para cada --cpus (1, 2, 4). Regra para ler: quando workers ≤ cpus, o ganho existe (ex.: 2 workers com --cpus=2 = 1,71x; 4 workers com --cpus=4 = 2,22x). Quando workers > cpus, piora. Se perguntarem de um ponto específico, olhe a tabela na seção 5.

Ponto fraco 5 — Variância (desvio padrão) e caso fora da curva

O sequencial teve desvio de 0,23 s (antes, 0,08 s), e 4 threads com --cpus=2 teve 0,36 s. Explique: máquina de uso geral, com Docker Desktop e outros programas rodando e núcleos de velocidades diferentes. Por isso fiz 5 repetições e reporto média ± desvio. Se o professor questionar, mostre que a conclusão (tendência) é a mesma nas execuções.

Ponto fraco 6 — "Seu Docker usa cgroups de verdade?"

Sim. Os dados finais foram coletados com docker run --cpus (Docker Desktop, que roda numa VM Linux). O script run_docker.sh tem um plano B (cgroups v2 via systemd-run) se não houver Docker. Se o professor usar outra máquina, as proporções devem se manter, mas os valores absolutos podem mudar.

Ponto fraco 7 — "Quanto custa a interface web?"

O cronômetro roda dentro do binário C++ (std::chrono), e o servidor Python só espera o processo terminar. Os números oficiais vieram dos scripts de terminal (benchmark_host.sh, benchmark_dock.sh), sem a interface.

6. Perguntas-armadilha extras

"E se eu aumentar para 100 workers?"
Piora: só há 12 threads lógicas; o resto vira troca de contexto e disputa de cache. O ideal é perto do número de núcleos.
"Qual a diferença entre concorrência e paralelismo?"
Concorrência é intercalar tarefas (1 CPU revezando, como em --cpus=1). Paralelismo é executar ao mesmo tempo em CPUs diferentes.
"O mutex é necessário se os blocos são disjuntos?"
Para escrever no dicionário, não. Para somar no checksum_global sim, pois todos escrevem na mesma variável. É a única região crítica.
"Por que o pai não usa o dicionário antes do waitpid?"
Porque os filhos ainda podem estar escrevendo. O waitpid garante que o dicionário está completo antes de cifrar.
"O que acontece se um filho morrer segurando o mutex?"
Os outros ficariam esperando para sempre (deadlock). No projeto o lock dura só uma soma e o filho não falha ali; mutex robusto (PTHREAD_MUTEX_ROBUST) seria a melhoria.

7. Resposta-relâmpago de 30 segundos

"Gerei um dicionário de 320 MB com 500 milhões de contas modulares. O sequencial leva 3,9 s. Dividi o trabalho em blocos contíguos, sem sobreposição, então não há corrida na escrita nem false sharing. Em processos usei mmap(MAP_SHARED) para escapar do Copy-on-Write; em threads a memória já é compartilhada. O checksum é a região crítica, protegida por mutex e acessada uma vez por worker. Com 8 workers, threads chegaram a 3,44x e processos a 3,32x, limitados por Amdahl, memória e núcleos não idênticos. No Docker com 1 CPU não há ganho nenhum: quanto mais workers, pior, por revezamento. Também investiguei uma diferença inicial entre processos e threads, descartei a hipótese da memória por medição e corrigi a causa real: o código gerado pelo compilador."
